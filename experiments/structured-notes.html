1. What changes in the note process?

The note writer receives the new 25–40 s transcript chunk, up to ten seconds of earlier speech for reference resolution, and one current note state. It never receives a future question. At question time, the reader retains the full available transcript and receives one current state.

Table 1. Note policies and the information passed between calls.
PolicyWriter inputWriter outputQuestion-time notes
Old · all snapshotsFull transcript prefix + all valid earlier snapshots.Another full snapshot, up to twelve notes.All valid snapshots.
Old · latest snapshotThe same saved old writer calls.No new writer calls in this control.Only the final eligible old snapshot.
Compact replacementNew chunk + recent reference speech + one earlier state.One replacement state: up to sixteen facts and eight changes.One current state.
Incremental editsNew chunk + recent reference speech + one earlier state.Up to six add/update/retire edits; an empty list means no change.One current state with up to sixteen facts and eight recent changes.

For incremental edits, the program assigns stable note IDs, checks source availability and rejects exact duplicate facts. When an edit marks a genuine revision, it saves the previous fact and source along with the new state. The full version archive remains on disk; the model receives the latest eight changes. Retired notes remain in the audit archive. A 4,096-token state limit guards memory growth; rejected updates and any capacity failures count in the audit.

Illustrative example: “A will send the invitation Friday” followed by “I will send it tomorrow instead” should update the same task and preserve the Friday → tomorrow change. A different task with a Friday deadline should keep a separate note. “I uploaded it” remains a speaker’s report until later speech verifies access.

2. Experiment and evaluation

  • Reuse both pinned Qwen3-30B readers, the original response prompt and the original request-time output limits.
  • Compare reactive, old-all, old-latest, compact replacement and incremental-edit conditions on the same six development questions.
  • Use one greedy Instruct run and two Thinking request seeds; earlier note generation uses seed 23.
  • Choose the policy using source-complete answers, unsupported claims, duplication, event changes and cost, then freeze it before the additional-meeting test.
  • Review final answers against source-based required facts; source-ID validity and JSON format are checked separately.

Thinking tokens are the model’s native reasoning tokens after the user request. Earlier thinking tokens are counted separately. Instruct exposes ordinary output tokens but no separate native thinking channel. Total generated tokens include earlier reasoning, note text, request-time reasoning, answer text and delimiters; they measure output volume rather than FLOPs. Each meeting’s writer calls count once per condition. The old-latest control retains the full old writer cost.

The additional test uses twelve questions in EN2004a, EN2006b, ES2003c, ES2006a, ES2007a, IB4003. These meetings were selected by split and timing metadata before development outputs were inspected; they are held out from this prompt-selection step. Later automatic-transcript checks reuse the existing anonymous speaker labels to avoid introducing changing annotation aliases.

5. Literature behind the design

The papers motivate explicit memory updates, self-contained facts and temporal links. Most compare retrieval-based or trained memories with other inputs; the present study tests prompt-only notes while retaining the transcript.

Literature gaps and full digest
  • Most reported token savings compare retrieved memory with full-history inputs; they do not directly establish lower native request thinking when the full transcript is retained.
  • Stable speaker ownership, disfluent speech and unresolved AMI discussion require source checks beyond schema validity.
  • A prompt-only incremental edit system may reduce copying but still merge distinct events or mistake intent for completion.

Compact replacement prompt

Record facts that help reconstruct the discussion: task owner and commitment, quantities and constraints, reasons and relationships, decisions and unresolved alternatives. Keep exact quantities, units, negation and qualifiers. Speaker is the source speaker; distinguish that speaker from a named task owner. Never infer task completion from an intention, file availability from an upload claim, agreement from an acknowledgement, or a calendar date from an unknown meeting date. Preserve relative times as spoken. No greetings, fillers, isolated 'okay'/'no', generic discussion summaries, repeated transcripts or anticipated questions. A short rejection can matter when it changes a specific proposal. Keep unresolved alternatives until speech resolves them. Old notes can be wrong: use new source speech to correct them. No outside knowledge. No participant-facing reply. Return only the requested JSON; do not add a prose introduction.

Reuse note IDs for the same event; assign a new ID only to a distinct event. Combine duplicate facts, and omit weaker details if necessary. The changes list records at most eight genuine revisions or resolved uncertainties, with the old and new state and source IDs. Keep a short previous-state description when a deadline, owner, quantity or decision changes; do not call a paraphrase a change. Preserve useful prior change entries. Unchanged notes appear once in the replacement snapshot, never as additional copies. Every source ID must be in the supplied transcript or earlier notes.
