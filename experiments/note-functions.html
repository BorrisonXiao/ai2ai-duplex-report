2. What each model receives and produces

At each existing 25–40 second transcript boundary, the Instruct note writer receives the new speaker-attributed speech, ten seconds of preceding context, one current note state and short receipts from the preceding edits. It sees neither the future question nor its reference answer. Both edit conditions decode freely with the same function descriptions, fields, operations and output cap.

The writer produces JSON operations or native Qwen function calls. The program validates each operation, executes accepted edits and assigns stable note IDs. The next update receives the changed state and receipts; previous snapshots are not accumulated. The current view is limited to 4,096 tokens and contains notes, eight recent changes and original transcript evidence. The full version history is retained on disk.

The common writer is Qwen3-30B-A3B-Instruct-2507. Final thinkers are the pinned Instruct and Thinking variants of Qwen3-30B-A3B-2507. Thinking reports native request-time reasoning tokens; Instruct has no separate thinking channel. Earlier note outputs are counted separately from request-time thinking.

3. Memory operations and changes

Table 4. Functions executed by the same memory store in both edit conditions.
FunctionEffect
add_note(topic, fact, owner, status, source_ids)Create a distinct fact, commitment or unresolved issue; return its note ID.
update_note(note_id, source_ids, optional changed fields)Change the same task/aspect using new speech; retain the earlier version and its evidence.
delete_note(note_id, reason)Remove a duplicate or mistaken note from the current view; retain the deletion record.
link_notes(first_id, second_id, relation)Connect existing notes through a revision, confirmation, explanation, qualification or reference.
no_change()Leave the notes unchanged.

Each note contains a topic, short factual text, owner, decision status and source IDs. Source IDs identify transcript passages; note IDs identify program-maintained notes. Add and update operations require at least one newly arrived source. The program rejects edits that break the function schema, cite unavailable speech, exceed size limits or lack that new evidence. Source words, speaker labels and timestamps are copied by the program. These mechanical checks do not establish that a generated fact or owner is correct.

Illustration: Friday is first proposed for sending the slides; Monday is later agreed. The current note changes to Monday, while the change record retains Friday and both supporting passages. A cancellation changes the plan’s status. Automatic budget eviction is recorded separately from model-requested deletion.

Exact function schemas and writer instructions

Flat arguments and one correction turn

The revised interface puts source IDs beside the other function arguments. If an output has invalid syntax or arguments, the program returns the error immediately and allows one correction generation for that segment. Accepted edits remain applied. Both generations and their complete inputs count toward the earlier token cost. Confirming a deadline should preserve the task owner; quantities and participant-specific access reports remain separate.

Why the first pilot was revised

The original interface produced three malformed outputs and 28 rejected operations across 134 updates. In authored controls it changed an owner when another speaker merely confirmed a deadline, confused posts with people, and skipped file-access changes. These errors blocked full evaluation. The revised pilot adds five controls with different speakers or values.

5. Evaluation and interpretation

The development set contains six previously inspected questions from five meetings, plus 10 authored checks for revised deadlines, distinct tasks, speaker ownership, file visibility and quantities with different meanings. Control cases are excluded from the 105-question scores and meeting token totals. Full evaluation requires development output review and a frozen design.

All 105 existing questions across 26 meetings are retained for the later comparison. Results will separately identify the 18 questions used in earlier note tuning and the 44 questions from other meetings; the full bank is not an unseen test set. Reference answers and scorer prompts are unchanged.

  • Report required-fact accuracy and fully supported accuracy, with invalid judge outputs shown separately.
  • Measure native request-time thinking tokens and actual first-answer/completion time; cold timing uses serial requests on one isolated H100.
  • Count all earlier input/output tokens, function definitions, receipts, rejected edits and unused updates, together with request-time costs.
  • Inspect duplicate facts, missed evidence, incorrect owners, changed decisions and notes dropped by the memory budget.

Useful edits must preserve answer quality and improve request-time work or cost. Function-call syntax alone does not establish a latency benefit. Notes plus transcript lookup is a later, separately gated comparison.
