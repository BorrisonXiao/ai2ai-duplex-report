# AMI questions asked during a meeting

The first pilot adds synthetic participant-to-assistant requests to the existing real EN2003a workshop-planning recording. The assistant is separate from A/B/C. Each example is an independent branch: play the original source prefix, pause at its source timestamp, present one synthetic question, allow the assistant to answer, then optionally resume. Synthetic reference answers never enter model inputs. An answer does not change the original meeting's subsequent decisions; this is a controlled replay, not a claim that the original participants would have continued identically after a real intervention.

EN2003a is a non-scenario AMI meeting. Its metadata contains speaker/channel mapping but no project-manager/designer role labels. The pilot uses explicitly marked perspectives inferred from prior speech. Official role-based experiments could subsequently use AMI scenario meetings with PM/ID/UI/ME annotations; those roles must not be imported into this recording.

## Text generation and review

Four generation/reader source cutoffs are 351.00, 1075.00, 1489.99 and 2135.50 seconds. They are outside annotated lexical words. Subsequent timing review found that 1489.99 is a word gap inside an unfinished sentence, so planned audio requests from that prefix move to 1578.92, after C completes a sentence and its half-second release delay has elapsed. Intervening speech discusses programme grouping and does not revise the cited outreach commitments; this was checked manually. Raw generation and reader probes retain 1489.99, and no reader result is claimed at the reanchored time. `replay_windows.json` supplies the distinct, extended planned replay context and source clock. The source pauses before inserted speech, so a question need not fit the original silence. Only transcript chunks whose last word has ended and whose assumed 0.5-second release delay has elapsed are available. This sentence-release policy can withhold words already heard in an unfinished sentence. It is an oracle-transcript preparation convention, not measured streaming ASR or an exact representation of all audible words at the cutoff. Source chunks are ordered by release time, with original start/end times retained to expose overlap.

Two local models, Qwen3-4B-Instruct-2507 and Qwen3-30B-A3B-Thinking-2507, each see the identical four prefixes. Two initial prompt settings ask for two questions per prefix: direct role-motivated generation and evidence-first generation with explicit old-history and revision requirements. One sampling seed (17), temperature 0.6 and top-p 0.95 make this a small exploratory comparison, not a statistically supported model ranking. The initial Thinking checkpoint has a 6,144-token generation allowance; the initial Instruct checkpoint has 2,048. At the user's request, review-v3 follow-up job 1110785 raises these to 16,384 and 4,096 respectively, with a 49,152-token context and 8 GiB KV cache. Real tokenizer preflight and per-model KV-size calculations pass. Both runs use vLLM with prefix caching and chunked prefill; v3 also enables CUDA graph/compiled execution instead of eager mode. Prompt, allowance and runtime differ in v3, so changes cannot be attributed solely to prompting. Token budgets include private reasoning where applicable. Truncated or unparsable outputs remain failures. Eight separately assistant-authored questions use the same prefix information and carry explicit origin labels.

Review checks are factual grounding, natural assistant-directed wording, requester motivation at that moment, preservation of tentative versus decided facts, answer completeness, attribution, lack of answer leakage in the question and necessity of earlier history. Every candidate receives an accept/revise/reject decision with a reason. Assistant review is not human annotation or an independent external judge. Preserve raw candidates and original references when publishing any edited version. The review set is for prompt development; a final benchmark must hold out meetings and question authors/prompts.

## Reading controls

The 4B reader receives a question and a transcript condition, with proposed answer, selected evidence and inferred role description withheld. Conditions are full available prefix, newest 60 seconds, question alone and prefix with selected evidence chunks removed. The initial job's recent condition keeps only chunks starting within the minute. During CPU review this was identified as an overly restrictive boundary, because an utterance can begin just before the window and contain recent facts. The follow-up keeps complete available chunks whose end overlaps the last minute and re-reads all initial and refined candidates. Use these follow-up controls for history judgments; preserve the initial stricter outputs as diagnostics. Full-prefix answers must recover the required facts; short-history answers must miss at least one required old fact for a history-dependent pass. A reader's own `fully_answerable` field is diagnostic only. Compare actual answer content and citations. Evidence removal can leave redundant evidence and is not automatically an unanswerability test. Same-model readback of 4B generations is marked as such; 30B and assistant-authored examples have a different reader model/origin, but no reader is assumed infallible.

All examples need atomic reference claims, exact source IDs/times/speakers, acceptable paraphrases and known stale or unsupported answers. For example, a planning capacity is not a count of confirmed speakers, and a spoken day number must not acquire an invented month. An unanswerable control needs an explicit absent fact and an abstention reference. Questions requiring visual slides, unrecorded email contents or inferred real names are excluded from audio-only evaluation.

## Later speech conversion

First approve the text and reference facts. Assign one consistent synthetic voice to each requester A/B/C, using new voices rather than claiming original AMI voices; assign a distinct assistant voice. Store source time, synthetic question duration, resampling, loudness and voice settings. A voice assignment conveys speaker identity only if the model has a valid way to map it to the prior speaker: generic TTS does not sound like an AMI participant. Start with explicit/oracle requester identity for this reason, and keep voice-only identity evaluation separate.

Synthesize question audio for model input. A reference-answer WAV is optional, useful for demonstration and listening QA; text plus atomic claims remains the primary scoring reference. Do not compare a generated answer to one reference waveform as if there were a unique correct voice or wording, and never feed reference-answer audio to the model. Independently transcribe generated question WAVs and inspect words, numbers and names before replay. Question and reference-answer TTS are not generated in the text pilot.

Maintain separate source and playback clocks. Pause/resume adds a question/response interval to playback time while source time remains fixed. Each example resets to its own prefix; no earlier synthetic answer is silently included. Continued-streaming or overlapping injection is a subsequent condition with its own no-future-information rule and latency clock beginning at the end of the injected request. No live duplex behavior or speech-model quality is established by this text-only generation run.

## Supervised evidence-packet setting

Whole-prefix v3 retained semantic and formatting defects in 4B Instruct despite larger caps. Job 1111068 therefore tests a distinct supervised selection setting: the primary assistant selects two small evidence packets per prefix, using only available utterances and checking the selected current state against the full prefix. The model receives the selected excerpts and requester perspective, with no assistant-authored question or proposed answer supplied. It composes one question/reference per packet. Selection assistance is explicit; this reduces retrieval burden and cannot be presented as the same unassisted task as v1–v3 or as a fair model ranking. Exact packets, prompts and provenance are retained.

This job uses one H100 SXM 80 GB, 4B Instruct only on GPU 0; a single resident vLLM engine serves generation and then reading sequentially. It depends on successful completion of 1110785, following 1110768; maximum one experiment GPU remains active. vLLM uses graph execution, prefix caching, chunked prefill, a 49,152-token context and 8 GiB KV cache. It also re-reads all candidates with hidden references, a 1,024-token reader allowance, a concise-answer instruction and at most eight citations. The original 512-token reader traces and their truncations remain preserved. Use the final reader outputs for content audits, and distinguish prompt/layout/cap effects from question validity.


## Completed pilot outcome

All three GPU jobs and CPU audit 1111132 completed. The 48 parsed raw drafts include 40 model generations and eight assistant-authored questions. Eight raw drafts are retained unchanged (six authored and two 30B paraphrases of one deadline intent). A ninth retained variant keeps the Instruct question verbatim and prunes its reference; `reference_edits.json` preserves the source link and exact edit. The nine variants cover seven intent groups. Raw draft tables exclude the derived reference edit from model pass counts. Two malformed packet outputs are preserved separately with review notes, never silently repaired.

The final bounded-citation reader produced 192 parseable responses, but fifteen contain citations outside the supplied context. Actual answer review identifies capacity-revision and speaker/audience errors despite positive answerability flags. Retained questions are source-backed evaluation candidates, not proof this reader solves them. The packet setting still failed to return the requested two questions per call and did not establish reliable automatic generation. A future scaled pipeline should use one evidence packet per request, constrained structured decoding and held-out meetings; that further configuration was not run here.

Actual allocations are 1,664 s + 546 s + 198 s = 2,408 GPU seconds / 0.668889 GPU hours. Each job used one H100 SXM 80 GB; all components were on logical GPU 0, sequential, with maximum one experiment GPU active. The first two jobs ran on gh116; the 4B-only packet job ran on gh110. All three runtime wrappers passed, default compute mode required no MPS, and no GPU job remains active. CPU audit, review and publication use zero GPUs. Slurm accounting and all frozen launch inputs remain in the workspace. No TTS was created.
