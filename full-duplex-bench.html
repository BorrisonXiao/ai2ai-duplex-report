Full-Duplex-Bench v3: tool use under real speech disfluencies

Definitions, caveats and sources

Coverage of the published evaluation protocol, not every task that could be built from the data. Model interface describes the intended input/output route; it does not imply that every capability of that model is evaluated.

Multi-party means a group setting, in text or audio. Synthetic describes the conversation/voice material; Mixed combines generated and human material. Target model: Text = text input/output; Audio→text = audio input, text/JSON output; Voice = voice interaction; Duplex = concurrent listening and speaking. Alternative adapters and text controls are listed below.

Content = semantic response scoring; Tools = call correctness; Timing = participation or response timing; User interruption = yielding/recovery when a user interrupts; Backchannels = generation or tolerance of brief acknowledgments; Speech quality = acoustic/prosodic scoring. A Yes does not imply comprehensive coverage. MSI bystander interference is distinct from directed user interruption. Source check: 2026-10-19.

Full-Duplex-Bench v3

Multi-speaker setting
No: one user speaker per recorded input clip; the task catalogue also defines a scripted agent turn.
Data origin
Human-recorded English speech from 12 speaker IDs, annotated for fillers, pauses, hesitations, false starts and self-corrections.
Input, protocol and model interface
Streaming voice-agent evaluation over recorded user audio, with local deterministic mock APIs and generated spoken responses.
Semantic response scoring
Yes: task completion, semantic tool arguments and spoken response content; GPT-4o judges argument and response quality.
Tool-call scoring
Yes: multi-step tool selection and argument correctness across four domains; pass@1 requires all expected calls and arguments.
Duplex and timing coverage
Yes: turn-taking, agent-start interruption rate and first-response, tool-call and task-completion latency.
What the scores do not establish
No multi-party conversation, real-service execution, dedicated user-barge-in recovery or acoustic speech-quality score. Mock APIs have zero service latency; hosted-model latency includes provider/network effects.

What the release contains

The v3 release is the newest dataset and code version listed by the upstream project as of this check. Its task catalog has 100 definitions; the audio archive has 100 recordings covering 79 unique scenario IDs, with repeated recordings for some scenarios.

100recorded user clips
79unique audio scenario IDs

4tool-use domains

The paper describes real human speech from 12 speakers and annotations for fillers, pauses, hesitations, false starts and self-corrections. The four domains use deterministic mock APIs, so they test tool selection, argument passing and spoken completion without contacting real services.

Full-Duplex-Bench also has v1, v1.5 and v2 releases. They use different evaluation protocols; this page covers v3’s downloadable multi-step tool-use audio set.

What the evaluation scores

Task completion requires correct calls and arguments

The benchmark reports tool-selection F1, semantic argument accuracy, response quality and strict Pass@1. Pass@1 requires the expected tool calls and correct arguments. GPT-4o judges semantic argument matches and whether the spoken transcript conveys the task result. Separate streaming measures include whether the agent takes a turn, latency to first speech/tool/factual completion, and the rate at which it begins speaking before the user finishes.

The APIs are deterministic local mocks with zero service latency. This isolates model and agent behavior from live-service variability; paper latency for hosted models still includes provider/network effects.

Integrity audit and release gaps

The downloaded archive is 702.0 MiB compressed and expands to 1.311 audio hours. Its ZIP CRC passes; all 100 metadata files parse, and all 100 PCM WAVs decode. The archive’s SHA-256 is 37545bd896f81718136598cf5be25d42ea9aa22efcd91f58370938d05d7d672f. The upstream archive did not include a checksum manifest, so this hash records the copy audited here rather than matching a publisher-provided digest.

The audio set does not contain one recording for every catalogue ID. It covers 79 of 100 scenario IDs; 21 catalogue IDs have no audio file. All non-dialogue task fields in the audio metadata match the pinned code catalogue for the overlapping IDs. The audio-side JSON stores one user turn, while the catalogue stores the scripted multi-turn exchange. The downloaded audio metadata marks 17 recordings for state rollback, compared with 21 rollback scenarios in the catalogue.

The paper describes the inputs as 48 kHz audio. The release contains three PCM layouts: 83 mono 48 kHz/32-bit WAVs, 10 stereo 48 kHz/32-bit WAVs and 7 mono 16 kHz/16-bit WAVs. Use each file’s actual header when preparing evaluation inputs.

At 100 clips and 12 speaker IDs, this remains a small single-user evaluation set. It has no group conversation, no real-service execution, no dedicated user-barge-in recovery test, and no acoustic speech-quality metric. Response quality is judged from transcription; it should not be read as a human-rated audio-quality score.
